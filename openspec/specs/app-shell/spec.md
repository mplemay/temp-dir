# app-shell Specification

## Purpose

Provides the web application's document shell, file-based routes, home page, and not-found handling so every request is served as a React full-stack page rather than a static SPA.

## Requirements

### Requirement: HTML document shell

The application SHALL serve every page inside a complete HTML document with UTF-8 charset, a responsive viewport meta tag, and a document title.

#### Scenario: Home page document

- **WHEN** a client requests `/`
- **THEN** the response is an HTML document that includes charset and viewport metadata and a non-empty title

### Requirement: Home page

The application SHALL render a home page at `/` that shows the committed ranked provider list as the primary content and does not present the previous vanilla Vite starter landing page or its client-only counter. Ranked rows MUST open the per-provider brief route. The home page MUST NOT present Market Intelligence, Product Knowledge, or CRM overview cards.

#### Scenario: Successful home visit

- **WHEN** a user opens `/`
- **THEN** they see a ranked provider list, with no Vite “Get started” copy, no “Count is” counter, and no Market Intelligence, Product Knowledge, or CRM overview cards

#### Scenario: Ranked list is visible

- **WHEN** a user opens `/`
- **THEN** they see providers in rank order with name, organization, tumor focus, incumbent lab, readiness, opportunity patient count, and a why-now line

#### Scenario: Home content is in the initial HTML

- **WHEN** a client fetches `/` without executing client JavaScript
- **THEN** the response body includes the home page heading and at least one ranked provider name

#### Scenario: Ranked row opens a brief

- **WHEN** a user activates a ranked provider row on `/`
- **THEN** they navigate to that provider’s brief page

### Requirement: Ranked list search, sort, and filter

The home ranked list SHALL let the user search by name and organization, sort columns, and filter by tumor focus, incumbent lab, and readiness. Default order SHALL be rank ascending. Those controls MUST NOT omit ranked provider names from the HTML returned without JavaScript.

#### Scenario: Default order is rank

- **WHEN** a user opens `/`
- **THEN** providers appear in rank order before any sort or filter is applied

#### Scenario: Search narrows rows

- **WHEN** a user searches the ranked list for a provider name
- **THEN** only matching rows remain visible

#### Scenario: Filter by incumbent

- **WHEN** a user filters the ranked list to one incumbent lab
- **THEN** only providers with that incumbent remain visible

#### Scenario: Names remain in the initial HTML

- **WHEN** a client fetches `/` without executing client JavaScript
- **THEN** the response body still includes at least one ranked provider name

### Requirement: Provider brief page

The application SHALL render a brief page at a per-provider path keyed by 10-digit NPI. The page SHALL show an overview joined from committed feeds and the ranked artifact, the meeting script from the briefs artifact, and the objection handler when `objection_response` is non-empty. Overview fields MUST NOT be generated by a model at request time. An NPI that is not in the ranked list SHALL use the not-found page.

#### Scenario: Overview is visible

- **WHEN** a user opens the brief page for a ranked provider
- **THEN** they see that provider’s name, organization, tumor focus, incumbent lab, rank, opportunity patient count, why-now line, and any CRM notes for that NPI

#### Scenario: Ranked signals are visible

- **WHEN** a user opens the brief page for a ranked provider
- **THEN** they see that provider’s readiness and impact score from the ranked artifact

#### Scenario: Extracted concern and interest are visible

- **WHEN** a user opens the brief page for a ranked provider whose ranked `concern` or `interest` is non-empty
- **THEN** they see that extracted text

#### Scenario: Meeting script is visible

- **WHEN** a user opens the brief page for a ranked provider
- **THEN** they see that provider’s meeting script

#### Scenario: Known objection is visible

- **WHEN** a user opens the brief page for a ranked provider whose `objection_response` is non-empty
- **THEN** they see the drafted objection response

#### Scenario: No concern hides the drafted objection

- **WHEN** a user opens the brief page for a ranked provider whose `objection_response` is empty
- **THEN** they see that no known concern was recorded and they do not see a drafted objection

#### Scenario: Brief content is in the initial HTML

- **WHEN** a client fetches a ranked provider’s brief path without executing client JavaScript
- **THEN** the response body includes that provider’s name and meeting script

#### Scenario: Unknown NPI is not found

- **WHEN** a user opens a provider brief path whose NPI is not in the ranked list
- **THEN** they see the not-found page

### Requirement: Unknown routes

The application SHALL render a not-found page for paths that do not match a defined route.

#### Scenario: Missing page

- **WHEN** a user opens a path with no matching route
- **THEN** they see a not-found message and the document remains a complete HTML page

### Requirement: Persistent sidebar navigation

The application SHALL show a sidebar on every page with links to Home, Market Intelligence, Product Knowledge, and CRM. The current page SHALL be visually distinguished in that navigation.

#### Scenario: Sidebar on home

- **WHEN** a user opens `/`
- **THEN** they see sidebar links for Home, Market Intelligence, Product Knowledge, and CRM

#### Scenario: Navigate from the sidebar

- **WHEN** a user activates the Product Knowledge sidebar link
- **THEN** they are taken to the product knowledge page

#### Scenario: Current page is marked

- **WHEN** a user is on the CRM page
- **THEN** the CRM sidebar item is marked as the current page

### Requirement: Market intelligence browse page

The application SHALL render a market intelligence page that lists accepted providers and accepted market events from the committed feed. The page MUST NOT rank providers or open a per-provider detail route.

#### Scenario: Providers are listed

- **WHEN** a user opens the market intelligence page
- **THEN** they see each accepted provider’s name, organization, tumor focus, incumbent lab, and opportunity patient count

#### Scenario: Events are listed

- **WHEN** a user opens the market intelligence page
- **THEN** they see each accepted market event’s headline and tumor type

### Requirement: Product knowledge browse page

The application SHALL render a product knowledge page that lists accepted assays from the committed feed. The page MUST NOT invent a numeric turnaround time or gene count that the feed left unpublished.

#### Scenario: Assays are listed

- **WHEN** a user opens the product knowledge page
- **THEN** they see each accepted assay’s display name, specimen, and regulatory status

#### Scenario: Unpublished metrics stay blank

- **WHEN** an accepted assay has a null turnaround time
- **THEN** the page does not show a numeric TAT for that assay

### Requirement: CRM browse page

The application SHALL render a CRM page that lists accepted notes from the committed feed. Each note SHALL show its date, body, and the matching clinician name when that NPI is present in market intelligence.

#### Scenario: Notes are listed

- **WHEN** a user opens the CRM page
- **THEN** they see each accepted note’s date and body

#### Scenario: Clinician name is shown

- **WHEN** a note’s NPI matches an accepted provider
- **THEN** that note is shown with the provider’s full name

### Requirement: Not-found stays in the app shell

When a path does not match a defined route, the not-found message SHALL appear inside the same document shell and sidebar as defined pages.

#### Scenario: Missing page still has navigation

- **WHEN** a user opens a path with no matching route
- **THEN** they see a not-found message and can still use the sidebar to reach Home
