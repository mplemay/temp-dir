# Spec Delta

## ADDED Requirements

### Requirement: Assay detail page

The application SHALL render an assay page at a per-assay path keyed by `test_id`. The page SHALL show display name, specimen, regulatory status, aliases, source URL, retrieved-on date, and the committed body. Unpublished TAT and gene count MUST stay blank. An unknown `test_id` SHALL use the not-found page.

#### Scenario: Assay fields are visible

- **WHEN** a user opens the assay page for an accepted assay
- **THEN** they see that assay’s display name, specimen, regulatory status, aliases, source URL, and retrieved-on date

#### Scenario: Body is visible

- **WHEN** a user opens the assay page for an accepted assay
- **THEN** they see the committed assay body text

#### Scenario: Unpublished metrics stay blank

- **WHEN** a user opens the assay page for an accepted assay whose turnaround time is null
- **THEN** the page does not show a numeric TAT for that assay

#### Scenario: Assay content is in the initial HTML

- **WHEN** a client fetches an accepted assay’s path without executing client JavaScript
- **THEN** the response body includes that assay’s display name and body text

#### Scenario: Unknown test id is not found

- **WHEN** a user opens an assay path whose `test_id` is not in the accepted catalog
- **THEN** they see the not-found page

### Requirement: Market event detail page

The application SHALL render a market-event page at a per-event path keyed by `event_id`. The page SHALL show headline, tumor type, event date, why-now text, and relevant tests joined to accepted assays. An unknown `event_id` SHALL use the not-found page.

#### Scenario: Event fields are visible

- **WHEN** a user opens the event page for an accepted market event
- **THEN** they see that event’s headline, tumor type, event date, and why-now text

#### Scenario: Relevant tests resolve to assays

- **WHEN** a user opens the event page for an accepted market event
- **THEN** they see each relevant test joined to at least one accepted assay display name

#### Scenario: Relevant test opens an assay page

- **WHEN** a user activates a relevant test on an event page
- **THEN** they navigate to that assay’s detail page

#### Scenario: Event content is in the initial HTML

- **WHEN** a client fetches an accepted event’s path without executing client JavaScript
- **THEN** the response body includes that event’s headline and why-now text

#### Scenario: Unknown event id is not found

- **WHEN** a user opens an event path whose `event_id` is not in the accepted events
- **THEN** they see the not-found page

### Requirement: CRM note detail page

The application SHALL render a note page at a per-note path keyed by `note_id`. The page SHALL show date, channel, body, the matching clinician name when known, and other accepted notes for the same NPI. An unknown `note_id` SHALL use the not-found page.

#### Scenario: Note fields are visible

- **WHEN** a user opens the note page for an accepted note
- **THEN** they see that note’s date, channel, and body

#### Scenario: Clinician name is shown

- **WHEN** a note’s NPI matches an accepted provider
- **THEN** the note page shows that provider’s full name

#### Scenario: Sibling notes are listed

- **WHEN** a user opens a note page whose NPI has other accepted notes
- **THEN** they see those other notes’ dates and bodies and do not see notes for a different NPI

#### Scenario: Sibling note opens its page

- **WHEN** a user activates a sibling note on a note page
- **THEN** they navigate to that note’s detail page

#### Scenario: Note content is in the initial HTML

- **WHEN** a client fetches an accepted note’s path without executing client JavaScript
- **THEN** the response body includes that note’s body

#### Scenario: Unknown note id is not found

- **WHEN** a user opens a note path whose `note_id` is not in the accepted notes
- **THEN** they see the not-found page

## MODIFIED Requirements

### Requirement: Provider brief page

The application SHALL render a brief page at a per-provider path keyed by 10-digit NPI. The page SHALL show an overview joined from committed feeds and the ranked artifact, the meeting script from the briefs artifact, and the objection handler when `objection_response` is non-empty. Overview fields MUST NOT be generated by a model at request time. An NPI that is not in the ranked list SHALL use the not-found page. Related assay names MUST open the assay detail route.

#### Scenario: Overview is visible

- **WHEN** a user opens the brief page for a ranked provider
- **THEN** they see that provider’s name, organization, tumor focus, incumbent lab, rank, opportunity patient count, why-now line, and any CRM notes for that NPI

#### Scenario: Ranked signals are visible

- **WHEN** a user opens the brief page for a ranked provider
- **THEN** they see that provider’s readiness and impact score from the ranked artifact

#### Scenario: Extracted concern and interest are visible

- **WHEN** a user opens the brief page for a ranked provider whose ranked `concern` or `interest` is non-empty
- **THEN** they see that extracted text

#### Scenario: Meeting script is visible

- **WHEN** a user opens the brief page for a ranked provider
- **THEN** they see that provider’s meeting script

#### Scenario: Known objection is visible

- **WHEN** a user opens the brief page for a ranked provider whose `objection_response` is non-empty
- **THEN** they see the drafted objection response

#### Scenario: No concern hides the drafted objection

- **WHEN** a user opens the brief page for a ranked provider whose `objection_response` is empty
- **THEN** they see that no known concern was recorded and they do not see a drafted objection

#### Scenario: Brief content is in the initial HTML

- **WHEN** a client fetches a ranked provider’s brief path without executing client JavaScript
- **THEN** the response body includes that provider’s name and meeting script

#### Scenario: Unknown NPI is not found

- **WHEN** a user opens a provider brief path whose NPI is not in the ranked list
- **THEN** they see the not-found page

#### Scenario: Related assay opens a product page

- **WHEN** a user activates a related assay on a ranked provider’s brief page
- **THEN** they navigate to that assay’s detail page

### Requirement: Market intelligence browse page

The application SHALL render a market intelligence page that lists accepted providers and accepted market events from the committed feed. The page MUST NOT rank providers. Provider names MUST open the per-provider brief route. Event headlines MUST open the market-event detail route.

#### Scenario: Providers are listed

- **WHEN** a user opens the market intelligence page
- **THEN** they see each accepted provider’s name, organization, tumor focus, incumbent lab, and opportunity patient count

#### Scenario: Events are listed

- **WHEN** a user opens the market intelligence page
- **THEN** they see each accepted market event’s headline and tumor type

#### Scenario: Provider row opens a brief

- **WHEN** a user activates a provider name on the market intelligence page
- **THEN** they navigate to that provider’s brief page

#### Scenario: Event row opens an event page

- **WHEN** a user activates an event headline on the market intelligence page
- **THEN** they navigate to that event’s detail page

### Requirement: Product knowledge browse page

The application SHALL render a product knowledge page that lists accepted assays from the committed feed. Assay names MUST open the assay detail route. The page MUST NOT invent a numeric turnaround time or gene count that the feed left unpublished.

#### Scenario: Assays are listed

- **WHEN** a user opens the product knowledge page
- **THEN** they see each accepted assay’s display name, specimen, and regulatory status

#### Scenario: Unpublished metrics stay blank

- **WHEN** an accepted assay has a null turnaround time
- **THEN** the page does not show a numeric TAT for that assay

#### Scenario: Assay row opens a detail page

- **WHEN** a user activates an assay name on the product knowledge page
- **THEN** they navigate to that assay’s detail page

### Requirement: CRM browse page

The application SHALL render a CRM page that lists accepted notes from the committed feed. Each note SHALL show its date, body, and the matching clinician name when that NPI is present in market intelligence. Note rows MUST open the CRM note detail route.

#### Scenario: Notes are listed

- **WHEN** a user opens the CRM page
- **THEN** they see each accepted note’s date and body

#### Scenario: Clinician name is shown

- **WHEN** a note’s NPI matches an accepted provider
- **THEN** that note is shown with the provider’s full name

#### Scenario: Note row opens a detail page

- **WHEN** a user activates a note row on the CRM page
- **THEN** they navigate to that note’s detail page
